# Provider setup and test workflow

Use a separate test Supabase project or local stack with Stripe and EasyPost test keys. Do not use real payment cards or purchase production postage while following this guide.

## Stripe Checkout and Tax

1. Create a Stripe account and select its test/sandbox environment.
2. Put the test secret key in `STRIPE_SECRET_KEY` and leave `COMMERCE_MODE=test`.
3. Enable/configure Stripe Tax for the test environment if using the default `STRIPE_AUTOMATIC_TAX=true`. Configure business origin, tax registrations, and the merchandise tax category appropriate to your store. Automatic calculation does not by itself establish your tax obligations or filing arrangements.
4. Install the [Stripe CLI](https://docs.stripe.com/stripe-cli) and sign in with `stripe login`.
5. Start the application with `npm run dev`. In a separate terminal, forward webhooks:

```powershell
stripe listen --forward-to http://127.0.0.1:3006/api/webhooks/stripe
```

Copy the displayed `whsec_...` into `STRIPE_WEBHOOK_SECRET` and restart the app. The CLI forwarding secret differs from a Dashboard endpoint's secret. Do not print it in shared logs or commit it.

Use the storefront to choose an in-stock product and variant, enter a valid US address, accept its verified form, select a returned shipping rate, and proceed to Stripe. Use `4242 4242 4242 4242`, any future expiry, and any three-digit CVC for a successful test payment. Stripe documents this flow in its [Checkout fulfillment guide](https://docs.stripe.com/checkout/fulfillment?payment-ui=embedded-form).

Check all of the following: the CLI receives the event, the server verifies it, the order appears in admin, its inventory decreases once, payment identifiers are saved, and queued notifications are delivered. Visiting the success URL alone must not create a paid order. A generic `stripe trigger checkout.session.completed` event is not a replacement for an actual store checkout: the fixture lacks this application's checkout attempt and reservation records.

For a deployed test or production store, register the HTTPS endpoint `/api/webhooks/stripe` in Stripe Workbench/Webhooks. Use the signing secret for that exact destination and the intended test/live mode. Subscribe to these handled events:

```text
checkout.session.completed
checkout.session.async_payment_succeeded
checkout.session.async_payment_failed
checkout.session.expired
payment_intent.payment_failed
refund.created
refund.updated
refund.failed
charge.refunded
```

Review `app/api/webhooks/stripe/route.ts` when changing the integration so the configured event list remains aligned with the code.

To test delivery retries, use Stripe Workbench's resend action on the event generated by your real test checkout. Verify there remains one order and one stock reduction. Stripe retries and may deliver events out of order, so the database deduplication is part of the payment flow. [Stripe webhook behavior](https://docs.stripe.com/webhooks)

Test refunds from the authenticated admin order page. Confirm the refund in Stripe and verify restocking is applied only for the intended returned/unshipped inventory. Never infer a successful refund from a button click alone. The admin supports full refunds; partial refunds created externally must be reconciled through the supported refund webhook flow.

## EasyPost addresses, rates, labels, and tracking

1. Create an EasyPost account, select test mode, and obtain its **test** API key.
2. Set `EASYPOST_API_KEY` and `EASYPOST_MODE=test`.
3. In admin settings, replace the example return/ship-from address with a valid address, including usable contact details.
4. Set measured parcel dimensions in inches and packaging weight in ounces in `.env.local`; edit variant weights in admin. The starter creates a single parcel from the item quantities and these measurements.
5. Test checkout with a valid US destination. EasyPost strict verification can correct spelling or ZIP formatting; the customer should review the returned address. An unverifiable address or failed rate request should show a recoverable error.
6. On a paid test order, retrieve available services in admin, review their costs, and buy a test label. Confirm the saved label URL, carrier, service, postage cost, shipment ID, Tracker ID, and tracking number.

Shipment rates come from the provider. Empty `rates` or carrier errors are not permission to fabricate a flat rate. Address verification may have per-country or account restrictions; this starter's domestic US scope avoids inventing international verification/customs behavior. [EasyPost addresses](https://docs.easypost.com/docs/addresses), [shipment API](https://docs.easypost.com/docs/shipments)

EasyPost needs a publicly reachable HTTPS endpoint. Use a deployed test environment or an HTTPS tunnel forwarding only to the local development server. Set a random `EASYPOST_WEBHOOK_SECRET`, then register the webhook using your test API key. The following PowerShell example assumes the two secrets are already present in your terminal environment; `.env.local` is not automatically loaded into your shell.

```powershell
$hookAuth = [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes("${env:EASYPOST_API_KEY}:"))
$hookBody = @{ webhook = @{ url = 'https://YOUR-TEST-DOMAIN/api/webhooks/easypost'; webhook_secret = $env:EASYPOST_WEBHOOK_SECRET } } | ConvertTo-Json -Depth 4
Invoke-RestMethod -Method Post -Uri 'https://api.easypost.com/v2/webhooks' -Headers @{ Authorization = "Basic $hookAuth" } -ContentType 'application/json' -Body $hookBody
```

Do not run registration repeatedly; retain the webhook ID, and update that webhook's URL/secret if needed. Register production separately with production credentials. EasyPost signs the raw body with HMAC SHA-256 in `X-Hmac-Signature`; the application checks the signature and deduplicates events. [Webhook registration and authentication](https://docs.easypost.com/docs/webhooks)

EasyPost provides test Tracker codes including `EZ1000000001` (pre-transit), `EZ2000000002` (in transit), `EZ3000000003` (out for delivery), and `EZ4000000004` (delivered). Submit a test Tracker to exercise webhook receipt:

```powershell
$trackerBody = @{ tracker = @{ tracking_code = 'EZ4000000004'; carrier = 'USPS' } } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri 'https://api.easypost.com/v2/trackers' -Headers @{ Authorization = "Basic $hookAuth" } -ContentType 'application/json' -Body $trackerBody
```

An independent test Tracker has no corresponding store shipment and should not update an unrelated order. To verify order delivery integration, use a test shipment created through the store and its associated Tracker or a documented test fixture mapped to that test order. Do not rewrite a production shipment's provider IDs to force a test. [EasyPost tracking tests](https://docs.easypost.com/docs/trackers)

If buying postage times out, consult the [operations runbook](operations.md) before retrying. Retrieve the existing shipment to determine whether a label was purchased; creating another shipment can buy duplicate postage.

## Resend transactional email

1. Add a domain or sending subdomain you control in Resend. A subdomain such as `mail.your-domain.com` can separate sending reputation from your main domain.
2. Add the exact DNS records shown by Resend to your DNS provider, including SPF and DKIM. Avoid creating duplicate SPF records for the same hostname; follow your provider's record-combination guidance.
3. Wait for Resend to report the domain verified. Set `RESEND_FROM_EMAIL` to a sender at that domain and `RESEND_API_KEY` to an authorized server key.
4. Set a deliverable `OWNER_NOTIFICATION_EMAIL` and review the owner mailbox in store settings.
5. Run the job endpoint to drain queued notifications and inspect delivery status in Resend.

Use Resend's permitted testing sender/recipient restrictions only for development. A valid API response is not proof that an inbox received the message; check delivery and bounce status during acceptance testing. [Resend verified domains](https://resend.com/docs/dashboard/domains/introduction)

Emails are transactional. Newsletter signup stores opt-in details; bulk campaigns, list migration, and marketing consent management are separate operational work. Do not treat a contact submission or purchase as marketing consent.

## Run the scheduled job locally

Set `CRON_SECRET` in both the app environment and your terminal environment, then:

```powershell
Invoke-RestMethod -Uri 'http://127.0.0.1:3006/api/jobs' -Headers @{ Authorization = "Bearer $env:CRON_SECRET" }
```

The job handles deferred notifications and reservation reconciliation. Local development does not run Vercel Cron automatically. Use this call after test actions and inspect application/provider records. Configure recurring execution before launch using [deployment.md](deployment.md).
